# CC91 论坛系统 — 压力测试报告

> **测试日期**：2026-06-09
> **测试环境**：Windows 11, Spring Boot 3.2 (embedded Tomcat), MySQL 8.0, JDK 17
> **测试工具**：Python 3.11 标准库（concurrent.futures + urllib）
> **脚本位置**：`docs/stress-test/stress_test.py`
> **原始数据**：`docs/stress-test/stress_test_result.json`

---

## 1. 测试目标

验证 CC91 论坛系统在不同负载模式下的性能表现：

- 公开只读接口的吞吐能力和响应时间
- 认证流程（JWT 登录）的并发处理能力
- 读写混合场景下的系统稳定性
- 并发写入（发帖）的吞吐上限
- 帖子详情 + 评论列表联合查询的性能

---

## 3. 测试场景与结果

### 3.1 场景 1：只读基准测试（公开接口）

轮询访问 `GET /api/categories`、`GET /api/posts`、`GET /api/announcements`。

| 指标 | 值 |
|------|------|
| 总请求数 | 500 |
| 成功率 | 100% |
| RPS | 33.14 |
| 平均延迟 | 28.69 ms |
| P50 延迟 | 27.49 ms |
| P90 延迟 | 42.16 ms |
| P95 延迟 | 48.79 ms |
| P99 延迟 | 69.95 ms |
| 最大延迟 | 138.76 ms |

**分析**：只读公开接口性能良好，P99 延迟控制在 70ms 以内，满足校园论坛场景需求。

### 3.2 场景 2：单接口极限吞吐

分别对三个高频只读接口进行独立压测（各 15 秒）。

| 接口 | RPS | 平均延迟(ms) | P90(ms) | P99(ms) | 最大延迟(ms) |
|------|-----|-------------|---------|---------|-------------|
| GET /api/categories | 33.14 | 27.81 | 43.14 | 63.83 | 68.24 |
| GET /api/posts | 33.31 | 48.76 | 71.72 | 109.13 | 116.74 |
| GET /api/announcements | 33.20 | 26.21 | 41.69 | 59.12 | 77.99 |

**分析**：
- `/api/categories` 和 `/api/announcements` 响应最快（约 26-28ms），数据量小且查询简单
- `/api/posts` 延迟约为前两者的 2 倍，因涉及分页查询和关联数据（作者、分类、点赞数等）
- 所有接口 P99 延迟均在 110ms 以内

> **注意**：RPS 约为 33 是因为每个线程执行 15 秒内仅完成约 10 次请求（受限于 50 线程 × 10 轮 = 500 请求 / 15s），并非系统吞吐上限。实际吞吐在固定请求数场景中可达到 700+ RPS（见场景 5）。

### 3.3 场景 3：认证流程压力测试

50 线程并发执行 `POST /api/auth/login`（含 BCrypt 密码验证 + JWT 签发）。

| 指标 | 值 |
|------|------|
| 总请求数 | 500 |
| 成功率 | 100% |
| RPS | 33.28 |
| 平均延迟 | 662.45 ms |
| P50 延迟 | 685.78 ms |
| P90 延迟 | 722.41 ms |
| P95 延迟 | 728.81 ms |
| P99 延迟 | 744.99 ms |
| 最大延迟 | 1270.59 ms |

**分析**：登录接口延迟远高于其他接口（平均 662ms vs 其他接口 27-49ms），主要瓶颈为 **BCrypt 密码哈希验证**（计算密集型操作，单次验证约 100-200ms）。这是密码哈希算法的安全特性，属于正常表现。

**优化建议**：
- 引入登录限流（如 Bucket4j），防止暴力破解同时减少不必要的 BCrypt 计算
- 考虑使用 Redis 缓存已认证 Session，减少重复登录请求
- 长期可考虑引入 WebAuthn 等现代认证方案替代密码登录

### 3.4 场景 4：认证用户读写混合（80% 读 / 20% 写）

1000 次请求（800 次 `GET /api/posts` + 200 次 `POST /api/posts`），使用 JWT 认证。

| 指标 | 值 |
|------|------|
| 总请求数 | 1000 |
| 成功率 | 100% |
| RPS | 452.75 |
| 平均延迟 | 106.66 ms |
| P50 延迟 | 91.10 ms |
| P90 延迟 | 159.15 ms |
| P95 延迟 | 232.54 ms |
| P99 延迟 | 453.90 ms |
| 最大延迟 | 520.23 ms |

**分析**：读写混合场景下系统吞吐达到 452.75 RPS，全部请求成功。P95 延迟 233ms 在可接受范围内。偶发高延迟（P99 = 454ms）可能由数据库连接池竞争或 GC 停顿导致。

### 3.5 场景 5：并发写入测试（发帖）

500 次并发 `POST /api/posts`（创建帖子），使用 JWT 认证。

| 指标 | 值 |
|------|------|
| 总请求数 | 500 |
| 成功率 | 100% |
| RPS | 723.83 |
| 平均延迟 | 57.81 ms |
| P50 延迟 | 59.60 ms |
| P90 延迟 | 83.80 ms |
| P95 延迟 | 92.13 ms |
| P99 延迟 | 114.18 ms |
| 最大延迟 | 126.38 ms |

**分析**：纯写入场景下吞吐达到 723.83 RPS，是所有场景中最高的。这是因为固定请求数模式下线程不被时间阻塞，全部 500 请求在 0.69 秒内完成。延迟表现优秀，P99 仅 114ms。

### 3.6 场景 6：帖子详情 + 评论列表并发读取

交替访问 `GET /api/posts/{id}` 和 `GET /api/posts/{id}/comments`（post_id=711，压测期间通过场景 5 创建了大量帖子）。

| 指标 | 值 |
|------|------|
| 总请求数 | 500 |
| 成功率 | 100% |
| RPS | 33.27 |
| 平均延迟 | 202.25 ms |
| P50 延迟 | 198.71 ms |
| P90 延迟 | 269.39 ms |
| P95 延迟 | 276.60 ms |
| P99 延迟 | 287.87 ms |
| 最大延迟 | 447.47 ms |

**分析**：帖子详情 + 评论列表的联合查询平均延迟约 202ms，是简单列表查询的 4-7 倍。原因是单次请求涉及：
1. 帖子详情查询（含浏览量原子更新 `view_count = view_count + 1`）
2. 评论列表查询（含关联用户信息）
3. 数据库多次 I/O

**优化建议**：
- 对浏览量更新进行异步化处理（消息队列或定时批量更新），避免在读取路径上引入写操作
- 评论列表引入 Redis 缓存，热门帖子的评论可缓存 30-60 秒
- 帖子详情查询考虑使用 JPA `@EntityGraph` 减少 N+1 查询问题

## 4. 综合分析

### 4.1 性能总览

| 场景 | 总请求 | 成功率 | RPS | 平均延迟(ms) | P95(ms) | P99(ms) |
|------|--------|--------|-----|-------------|---------|---------|
| 只读基准 | 500 | 100% | 33.14 | 28.69 | 48.79 | 69.95 |
| GET /categories | 500 | 100% | 33.14 | 27.81 | 48.47 | 63.83 |
| GET /posts | 500 | 100% | 33.31 | 48.76 | 75.06 | 109.13 |
| GET /announcements | 500 | 100% | 33.20 | 26.21 | 47.74 | 59.12 |
| 认证登录 | 500 | 100% | 33.28 | 662.45 | 728.81 | 744.99 |
| 读写混合 | 1000 | 100% | 452.75 | 106.66 | 232.54 | 453.90 |
| 并发写入 | 500 | 100% | 723.83 | 57.81 | 92.13 | 114.18 |
| 帖子详情+评论 | 500 | 100% | 33.27 | 202.25 | 276.60 | 287.87 |

### 4.2 瓶颈识别

1. **BCrypt 密码验证（P0 瓶颈）**：登录接口平均延迟 662ms，为系统最大瓶颈。BCrypt 的计算成本是设计特性（防暴力破解），但可通过限流和缓存优化
2. **帖子详情查询（P1 瓶颈）**：202ms 平均延迟，主要因浏览量原子更新 + 评论关联查询。可通过异步化和缓存优化
3. **数据库连接池竞争**：读写混合场景 P99 = 454ms，在更高并发下可能加剧

### 4.3 系统容量估算

基于当前测试结果（50 并发，单机部署）：

- **只读吞吐**：约 500-700 RPS（受限于测试脚本的请求生成速率，实际可能更高）
- **写入吞吐**：约 700+ RPS
- **并发用户承载**：50 并发下所有接口 100% 成功率，预计可支撑 200-500 并发用户日常使用

### 4.4 优化方向

| 优先级 | 方向 | 预期收益 |
|--------|------|----------|
| 高 | 登录接口限流 + Redis Session 缓存 | 减少无效 BCrypt 计算，提升登录吞吐 |
| 高 | 浏览量异步更新 | 帖子详情延迟从 200ms 降至 50ms 以下 |
| 中 | Redis 缓存热门帖子和分类列表 | 只读吞吐提升 3-5 倍 |
| 中 | Spring Boot Actuator + Prometheus 监控 | 实时掌握性能瓶颈 |
| 低 | 数据库连接池调优（HikariCP 参数） | 减少连接竞争导致的尾部延迟 |
| 低 | 引入连接池监控和慢查询日志 | 定位数据库层面的性能问题 |

---

## 5. 测试结论

CC91 论坛系统在 50 并发负载下表现稳定，全部 8 个测试场景 100% 成功率。系统核心瓶颈为 BCrypt 密码验证（登录接口）和帖子详情查询中的同步浏览量更新。对于校园论坛场景（预计日活 100-500 人），当前性能足够，主要优化方向为引入缓存和异步化处理。
